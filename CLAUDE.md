# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

A three-tier sample app: Vue 3 SPA built with Vite (`frontend/`) → REST service on Tomcat 8.5 (`backend/`, Java 8, Jersey 2.24 + Jackson) → MySQL (`database/`). Code, comments, DB columns and error messages are in Spanish; keep that convention. Not a git repo; no Maven/Gradle, tests or linter. The target runtime (per the original course instructions) is Tomcat **8.5.99 + JDK 8** with `javax.*` APIs — do not move to Tomcat 9+/10 or a newer JDK (Jersey 2.24 / HK2 breaks on modern JDKs). Development is local only; nothing is deployed yet.

## Commands (run from the repo root)

```
./setup.sh        # once: downloads JDK 8 -> ./jdk8, Tomcat 8.5.99 -> ./tomcat (webapps emptied, ROOT created),
                  #       Jersey 2.24 jars -> backend/WEB-INF/lib (+ jars from dependecies/), npm install in frontend/.
                  #       Idempotent, no sudo. Node.js is NOT downloaded: the user has it installed (via nvm).
cp .env.example .env   # then set DB_USER / DB_PASSWORD
./build.sh        # javac -> backend/WEB-INF/classes -> backend/servicio.war -> replaces tomcat/webapps/servicio{,.war} (the old capitalized Servicio{,.war} is removed too);
                  #   then `npm run build` in frontend/ and replaces tomcat/webapps/ROOT with frontend/dist.
                  #   A running Tomcat redeploys automatically.  ./build.sh back | front  builds only one side.
                  #   If the PRODUCTION Tomcat is running (background "catalina.sh start": scripts/inicia.sh PID file or pgrep;
                  #   ./dev.sh uses "run"), it only compiles and leaves webapps alone unless --despliega is passed.
./dev.sh          # runs catalina in the foreground (Ctrl+C to stop);  ./dev.sh stop  stops another instance
scripts/inicia.sh     # production scripts live in scripts/ (documented in scripts/README.md, keep it in sync): inicia.sh = catalina start
                      #   in background (nohup, PID tomcat/temp/catalina.pid, log catalina.out; needs DB_USER + servicio.war); detiene.sh stops it;
                      #   arranque.sh [--deshabilita|--estado] = marked @reboot crontab entry; certificado.sh <dominio> [--correo][--webroot][--staging]
                      #   = sudo certbot -> openssl pkcs12 tomcat/conf/certificado/servicio.p12 -> marked HTTPS Connector (HTTPS_PUERTO 8443) before
                      #   the first non-commented <Engine>, self-registered as certbot --deploy-hook (--hook), --quita; puertos.sh = iptables/ip6tables
                      #   nat REDIRECT 80->8080, 443->8443 tagged "servicio-web" (--local, --quita, --estado, --persistente systemd unit).
                      #   They source scripts/common.sh (shared helpers: puerto_http/puerto_https/puerto_ocupado, PID_PRODUCCION, markers).
                      #   Target is another (server) machine, not this dev box.
./dev.sh front    # Vite dev server on :5173 (HMR), proxies /servicio -> localhost:8080 (Tomcat must be running)
source test/login.sh <email> [pw]  # exports API_BASE/ID_USUARIO/TOKEN; then ./test/<endpoint>.sh [args] prints + runs its curl; ./test/todos.sh = store walkthrough
```

URLs: service `http://localhost:8080/servicio/rest/ws/<endpoint>`, client `http://localhost:8080/` (or `http://localhost:5173/` with `dev.sh front`). There is no unit-test framework; `test/` holds curl-based bash tests (see below), and the client can be checked by hand. The database is created manually by the user with `database/schema.sql` (do not run it on their behalf).

## Tests (`test/`)

One **self-contained** bash script per endpoint (`test/<endpoint>.sh`, no shared lib): each writes its `curl` explicitly, **prints the curl command using the env vars** (`$API_BASE`, `$ID_USUARIO`, `$TOKEN`; copy-pasteable in that shell), then the HTTP code and the body (long base64 abbreviated with jq `walk`). Service URL and session come from env vars `API_BASE`, `ID_USUARIO` and `TOKEN` (every script except login exits 2 if `API_BASE` is unset), exported by `source test/login.sh <email> [contraseña]` (prompts for the password if omitted; sends its SHA-256; executed instead of sourced it prints `export ...` lines for `eval`). Endpoint arguments are positional (see each script's header); JSON bodies are built with jq into `${TMPDIR:-/tmp}/<endpoint>.json` and sent with `--data-binary @file`. `RESPUESTA=<file>` makes a script copy the raw body there. `test/todos.sh [email]` runs a store walkthrough with the current session (creates an article "Prueba <fecha-hora>" that stays in stock, empties the whole cart) and prints a PASS/FAIL summary; it never runs alta/modifica/borra_usuario. `borra_usuario.sh` asks for confirmation (`--si` skips). Exit code 0 = HTTP 200, 1 = service error, 2 = missing session/args or no connection. login.sh defaults `API_BASE` to `http://localhost:8080/servicio/rest/ws`. **When you add or change an endpoint, add/update its `test/<endpoint>.sh` (same style: explicit curl, printed with env vars, URL + session from env) and `todos.sh` if relevant, together with `openapi.json`.**

`backend/compila.sh` / `compila.bat` are the original course scripts; they are superseded by `build.sh` and no longer compile (the service now needs Tomcat's `tomcat-dbcp.jar` on the classpath).

## Configuration (environment variables)

`scripts/common.sh` (sourced by setup/build/dev and the scripts/ production scripts) loads `.env` if present and otherwise falls back to the OS environment; **`.env` wins over the OS** when both define a variable. Variables: `DB_HOST` (localhost), `DB_PORT` (3306), `DB_NAME` (servicio_web), `DB_USER` (required), `DB_PASSWORD`; optional `HTTPS_PUERTO` (8443), `CERT_CORREO`, `JAVA_HOME` (default `./jdk8`), `CATALINA_HOME` (default `./tomcat`), `VITE_HOST_SERVICIO` (host of the REST service for the client, e.g. `http://server:8080`; default same origin; the `/servicio/rest/ws` path is fixed; read in `frontend/src/api/servicio.js` via `import.meta.env`, baked in at build time — the exported var reaches Vite through `build.sh`/`dev.sh front`, or use `frontend/.env`). `dev.sh` exports them and Tomcat's JVM inherits them; `Servicio.java` reads them with `System.getenv`. So the service only gets DB config when Tomcat is started from a shell that has the variables (e.g. via `dev.sh` or `scripts/inicia.sh`).

## Architecture

- **All endpoints live in one class**, `servicio/Servicio.java`; `Usuario` (request/response DTO with public fields, `foto` as `byte[]` ⇒ base64 in JSON) and `Respuesta` (`{"mensaje": ...}`) are the only other classes. Jersey discovers resources by scanning package `servicio` (`web.xml`, mapped to `/rest/*`; class `@Path("ws")`). CORS is open to any origin through Tomcat's `org.apache.catalina.filters.CorsFilter` in `web.xml` (mapped to `/rest/*`, `*` without credentials — the session travels in `id_usuario`/`token`, not cookies), so the client can be served from another host (`VITE_HOST_SERVICIO`).
- **DB access**: plain JDBC. The pool is a Tomcat-bundled `org.apache.tomcat.dbcp.dbcp2.BasicDataSource` built in a static initializer from the env vars above (not JNDI anymore). `setDriverClassLoader(Servicio.class.getClassLoader())` is required because the pool class is loaded by Tomcat's loader while the MySQL driver sits in the webapp's `WEB-INF/lib`. `tomcat-dbcp.jar` is compile-time only (provided by Tomcat at runtime).
- **Auth model**: `GET login` checks email + password and writes a fresh random 20-char token into `usuarios.token`, returning `{id_usuario, token}`. Every other endpoint takes `id_usuario` and `token` query params and calls `verifica_acceso()` first. One token per user (a new login invalidates the previous one). Passwords are SHA-256 hashed **client-side** (`frontend/src/utils/sha256.js`, UTF-8; same output as the original `prueba.html` for ASCII); the server stores/compares that hash as-is (fits `varchar(64)`).
- **Endpoints**: `GET login`, `POST alta_usuario`, `GET consulta_usuario`, `PUT modifica_usuario`, `DELETE borra_usuario`; tienda: `POST alta_articulo`, `GET consulta_articulos`, `PUT compra_articulo`, `GET consulta_carrito_compra`, `DELETE elimina_articulo_carrito_compra`, `DELETE elimina_carrito_compra`. Tablas `stock`, `fotos_articulos` (foto obligatoria, una por artículo) y `carrito_compra` (índice único `(id_usuario,id_articulo)`, FKs a `usuarios` y `stock`). `Articulo` es el DTO (`@JsonInclude(NON_NULL)`; en el carrito `cantidad` = cantidad comprada). Compra/eliminación mueven cantidades stock⇄carrito en una transacción con `SELECT ... FOR UPDATE`; `vacia_carrito()` (usado por `elimina_carrito_compra` y `borra_usuario`) regresa el carrito al stock. **Connection rule (all endpoints):** `pool.getConnection()` must be immediately followed by a `try/finally` that closes it, and `verifica_acceso()`, validations and `setAutoCommit(false)` go *inside* it (or validations go before `getConnection()`); an early `return`/`throw` outside that block leaks a pooled connection (pool max is 100). For transactions use an outer `try/finally { conexion.close(); }` around `setAutoCommit(false); try { ...; commit } catch { rollback; throw } finally { setAutoCommit(true) }`. Photos live in `fotos_usuarios` (at most one row per user): modify = delete the photo row, then re-insert if provided; delete user = delete photo row then user row, in one transaction.
- **API contract (`openapi.json`, repo root, OpenAPI 3.0.3)**: hand-maintained description of every endpoint (paths, query params, request/response schemas, error convention). **ALWAYS update `openapi.json` in the same change whenever the REST API is modified** — adding, removing or renaming an endpoint, HTTP method or parameter, or changing a request/response field of `Usuario`, `Articulo` or `Respuesta`, validations/error messages, or the base URL (`/servicio/rest/ws`). Keep it in sync with `Servicio.java` and the DTOs, then check the file is still valid JSON (`python3 -m json.tool openapi.json`) and that every `$ref` resolves. Also keep the "Endpoints del servicio REST" section of `README.md` (index table + per-endpoint descriptions) consistent.
- **Error convention**: every handler wraps its body in try/catch and returns HTTP 400 with a `Respuesta` JSON body (also for "Acceso denegado"); success is 200. The client branches on `ok` (status 200) and shows `datos.mensaje` in the modal.
- **Dates/JSON**: the shared `ObjectMapper j` uses `yyyy-MM-dd'T'HH:mm:ss.SSS`; responses are built manually with `j.writeValueAsString(...)`, while request bodies are deserialized by Jersey's Jackson feature.
- Resource handling is deliberately verbose nested try/finally closing of `Statement`/`ResultSet`/`Connection` (no try-with-resources); follow it when adding endpoints.
